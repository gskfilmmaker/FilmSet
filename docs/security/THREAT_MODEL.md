# FilmSet — Threat Model

**Audit deliverable 7 of 11.** Covers Part 26. Every threat below is evaluated against the *actual* current architecture (`CURRENT_ARCHITECTURE_MAP.md`), not a generic checklist — "existing control" and "missing control" columns reflect what's really in the repository today, verified by reading it, not assumed.

**Severity scale**: Critical (exploitable today, high impact) · High (exploitable today or trivially soon, moderate-to-high impact) · Medium (requires a specific precondition) · Low (theoretical / requires the platform to grow into the risk first).

| 1 | Stolen credentials | Any production's data | External attacker with phished/leaked password | Sign in with stolen email+password — no MFA exists to stop them (`AUTHORIZATION_GAP_ANALYSIS.md` §9) | Password auth via Supabase; RLS still limits blast radius to productions that user is a member of | MFA, login-anomaly detection, session visibility for the victim to notice/revoke | Ship MFA (`SECURITY_ARCHITECTURE_V1.md` §3) before FilmSet holds materially sensitive productions | **High** |

| 17 | AI data leakage | Production data sent to Anthropic's API | Overly broad context passed into a Suggest call | `apps/web/lib/ai.ts` functions receive only the specific snapshot/document text relevant to the call, not a full-database dump — a reasonable existing practice, but not formally reviewed against a data-minimization policy | No documented policy on what's in/out of scope for AI context; no redaction of sensitive fields before an AI call | Formalize a data-minimization review for every `lib/ai.ts` function as sensitivity classification (Part 9) lands — a `HIGHLY_CONFIDENTIAL` field should not silently flow into an AI prompt without an explicit decision that it should | Review during Part 9 rollout (P1/P9) | Medium |

## Notable Pattern Across This Model

The two **existing** controls worth naming explicitly as real strengths (#12, #18) both come from the same source: FilmSet's RLS tenant isolation and its AI governance chain were both built with real discipline, not bolted on. The **highest-severity gaps** (#2, #5, #10) all trace back to the same missing piece: a centralized, DENY-by-default authorization engine (`SECURITY_ARCHITECTURE_V1.md` §1). This is why `IMPLEMENTATION_ROADMAP.md` sequences the permission engine as P1, ahead of every logistics feature — it is this threat model's single highest-leverage fix, closing three Critical/High threats at once rather than one at a time.
